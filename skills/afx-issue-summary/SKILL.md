# AFXX 修复总结

## 输入与证据读取

接收 issue、源码仓库和修复 commit（或明确的未提交差异）、基线、现有证据位置、平台 verify/回归轮次、输出位置，以及使用非默认环境时的任务配置。优先沿用当前任务已知信息；交接允许包含本地路径，不要求另建交接文件。

独立调用时先核对已有源码与任务记录，区分基线、阶段候选和最终修复。读取 diff 及相关上下游实现，按需读取实际 IR、日志和测试记录；仅有旧总结中的断言不能当作重新核验的证据。缺少材料时先从已有记录查找，仍不可得则注明缺口，不自动重新部署或复测，不修改修复代码或创建 commit。

平台信息通过 AFXX 的只读 issue/status 查询获取，不自行拼 HTTP。读取证据可参考 [复现证据清单](../afx-issue-repair/references/replay-evidence.md) 和 [平台查询说明](../afx-issue-repair/references/platform-evidence.md)；这不授权执行修复流程。按需读取相关字段和文件，不把全部 dump 放入上下文。无法确认已验证源码与修复 commit 一致时，明确列为证据缺口，不宣称验证覆盖该提交。

## 生成总结

直接生成 [summary.yaml](assets/summary.yaml)，不另建需手工转换的正文。顶层使用平台知识字段 kind、title、symptom、root_cause、solution，以及 fix_ref、body_md；不加 knowledge 外层或自建 evidence、issue_id 顶层字段。fix_ref 使用真实修复 commit，未提交时省略。

按 [总结模板](assets/summary.yaml) 写技术总结：顶层字段简述现象、根因和方案，正文重点展开“实际错误片段 → 错误机制 → 修复行为 → 验证依据”。多条独立根因分别分析，不能用一串源码位置或 job 引用代替解释。
- “错误机制”从输入或上游语义追溯关键类型、属性或操作如何产生、如何转换及在哪一步违反约束，只展开与根因有关的链路。“修复行为”解释为何保持原始语义；替换操作、放宽判断或新增分支时说明选择依据、适用边界和后续处理支持，有直接替代方案时简述取舍，不能仅以报错消失证明合理。
- 从实际 dump 摘录最小 IR，保留理解类型、操作数和变换所需的上下文，附一行来源说明。总结应独立可读：不写本地或远端机器的绝对路径；源码与测试使用仓库相对路径和符号名，由 fix_ref 固定版本。外部引用仅使用可共享的平台记录或归档附件，没有时说明产物类型（如“基线 AFIR dump”），原始路径留在任务记录。无 IR 的问题使用实际日志、代码或输入输出对照。修复后 IR 也必须来自实际产物；没有时说明转换规则，缺失现场如实注明，不根据修复代码编造。
- 正文只保留必要复现条件和基线 SHA。deploy/request/attempt ID、环境目录、包哈希和构建流水账留在任务记录，除非它们直接解释本次根因。每条根因的“验证依据”写测试覆盖的语义和实际结果，区分编译通过、输出正确与边界行为保持；测试应对应修复依赖的语义假设，尚未证明的部分列为人工检视重点，不写成确定结论，影响结论的限制就近说明；不另设验证汇总章节。正文末尾只保留一行平台地址、issue ID、verify/关联 regression 轮次与结果；skip、未运行和无回归候选不计通过。
- 人工检视重点列具体语义和受影响分支；同类问题定位指引给出识别信号、排查方法、预期观察与适用边界。不粘贴整份 dump，不为整理总结自动上传附件。

## 检查与交付

检查 YAML 可解析、必填项非空、占位符已替换或删除，结论与实际证据一致。缺失信息注明原因，不伪造 SHA、用例数、IR 或通过结果，不包含凭据或无关敏感日志。

默认写到 `<local.state_dir>/issues/<issue-id>/summary.yaml`，用户指定路径时沿用；从任务配置解析 state_dir，不猜环境或硬编码目录。总结放在源码 worktree 外，不随源码同步。更新已有总结时以当前修复证据为准，保留仍有效的技术分析。

交付文件绝对路径、修复 commit（若有）和影响检视的证据缺口，标记“待人工检视”。本 skill 不执行 issue summarize、不上传附件、不关闭 issue。人工检视后如用户明确要求发布，再按 [平台提交说明](../afx-issue-repair/references/platform-evidence.md) 执行独立命令；生成总结不代表平台已 resolved 或代码已合入。
